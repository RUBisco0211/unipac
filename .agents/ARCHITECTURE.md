# UniPac Wails Architecture

This document describes the current architecture of `unipac-wails` and the direction future agents should follow. `unipac-wails` is the primary project. The old Tauri project is no longer a maintained target and should not be modified.

## High-Level Shape

UniPac is a Wails desktop application with a Go backend and a Vue frontend.

- `main.go` configures the Wails app window, menu, embedded frontend assets, startup/shutdown hooks, and binds the backend `App` object to JavaScript.
- `app.go` is the Wails-facing application service. Exported methods on `App` become frontend-callable methods under `frontend/wailsjs/go/main/App.*`.
- `backend/` owns package-manager discovery, command execution, cache persistence, config, and logging.
- `frontend/` owns presentation, routing, page state, i18n, table rendering, and calls into the Wails bindings through `src/lib/api.ts`.
- `frontend/wailsjs/` is generated by Wails. Do not edit it by hand.

The intended dependency direction is:

`frontend pages/components` -> `frontend/src/lib/api.ts` -> `wailsjs generated bindings` -> `App` methods -> `registry/cache/adapters/util`.

Frontend code should not call generated Wails bindings directly outside `src/lib/api.ts`, except for Wails runtime concerns such as events/window controls.

## Backend Modules

### App Boundary

`app.go` is currently the public backend API exposed to the frontend.

Current exported methods:

- `InitManagerRegistry()`
- `ListManagers() []manager.Info`
- `ListEnabledManagers() []manager.Info`
- `GetCachedPackages() ([]manager.Package, error)`
- `UpdateCache() error`

These methods are the coarse UI-facing operations. New frontend-visible package actions should generally be added here first, then Wails bindings regenerated.

### Manager Core

`backend/core/manager/` defines shared backend domain types:

- `Info`: manager metadata such as `id`, executable name, display name, enabled state, executable path, and capabilities.
- `Capabilities`: feature flags reported by an adapter.
- `Package`: normalized package data used by the registry, cache, Wails bindings, and frontend.
- `Adapter`: interface implemented by package-manager integrations.
- `ActionResult` and `ActionOptions`: common command result and options types.

The backend manager registry is the source of truth for which package managers exist. The frontend must not maintain a parallel list of managers such as `brew`, `npm`, `pip`, or `cargo`.

### Registry

`backend/core/registry/registry.go` owns adapter registration and orchestration.

Current behavior:

- Builds adapter instances from `backend/adapters.GetAdapterConstructors()`.
- Runs adapter `Preflight()` and marks managers enabled or disabled.
- Returns all manager metadata through `ListManagers()`.
- Collects installed packages from enabled adapters with `ListInstalled` capability.

Important current issue:

- The closure inside `GetInstalledPackages()` captures the loop variable `adp`. The source comment notes this risk. Future work should pin the per-iteration adapter before appending the collector.

The registry should be the only backend component that knows about all adapters as a group. UI-level operations like search/install/update/uninstall should be added as registry methods that route by `manager.ID` and check `Capabilities`.

### Adapters

`backend/adapters/` contains concrete package-manager integrations.

- `index.go` statically registers adapter constructors.
- `brew/` has the most complete implementation for listing installed packages and outdated data.
- `npm`, `pip`, `pipx`, and `cargo` are mostly skeletons or partial stubs.

Adding a package manager should require backend-only changes:

1. Implement `manager.Adapter`.
2. Add the constructor to `backend/adapters/index.go`.
3. Ensure `Info.ID`, `Info.Name`, `ExecName`, and `Capabilities` are correct.
4. Let the frontend discover it through `ListManagers()`.

No frontend hardcoded manager list should be required.

### Cache

`backend/cache/` stores installed package snapshots in SQLite.

- Default path: `cache/package.db` under `util.AppRoot`.
- Schema table: `installed_package_cache`.
- `List()` returns cached packages.
- `UpdateCache()` currently deletes all rows and inserts the latest scan result.

Current behavior to note:

- If `UpdateCache()` receives an empty package list, it returns without clearing old cache data. Decide whether this is intentional before relying on it.
- Cache is initialized during app startup and startup currently calls `UpdateCache()`, meaning launch can block or fail if package scanning fails.

### Config and Logging

`backend/config/config.go` loads or creates `unipac.json` under the app root. It writes default cache/log config and snapshots current manager metadata into config.

`backend/logging/logging.go` initializes `slog` to stderr and app log file.

Current issue:

- `logging.Init` calls `LogFile.Close()` inside an error path even when `os.OpenFile` failed and `LogFile` may be nil. This should be guarded.

### Util

`backend/util/` contains shared helpers for:

- App root and safe path creation.
- JSON file read/write.
- Command execution and line collection.
- Parallel collection.
- Wails dialogs.

Command helpers are backend-only. The frontend should request operations through `App` methods rather than constructing package-manager commands.

## Frontend Modules

### API Boundary

`frontend/src/lib/api.ts` is the frontend adapter around generated Wails bindings.

Its responsibilities:

- Hide Wails generated type details from pages/components.
- Normalize backend JSON fields into frontend-facing TypeScript models.
- Provide stable functions such as `listManagers`, `loadCachedPackages`, and `reloadPackages`.

This file is the correct place to adapt naming differences like backend `list_installed` to frontend `capabilities.list`.

Avoid direct imports from `frontend/wailsjs/go/main/App` in pages, components, or composables. `App.vue` currently imports `GetCachedPackages` directly for logging; that should be removed or routed through `src/lib/api.ts`.

### Manager Discovery

`frontend/src/composables/useManagers.ts` loads manager metadata via `listManagers()` and exposes:

- `managers`
- `enabledManagers`
- `managerNameMap`
- `hasManager`
- `loadingManagers`

This is the correct source for manager filters, labels, and capability-aware UI.

Frontend code should treat manager IDs as opaque strings. It can display a manager's backend-provided `name`, color a badge from the ID hash, and use capabilities to enable/disable actions, but should not branch on concrete IDs.

Current hardcoded manager knowledge:

- `frontend/src/lib/format.ts` defines `managerLabelMap` with specific managers. This should be removed in future cleanup and replaced with `managerNameMap` from `useManagers()` or backend-provided names.

### Pages

Current pages:

- `Packages.vue`: installed package inventory, cache loading, refresh, filtering, selection, package actions.
- `Outdated.vue`: outdated-only package view, built from the same table/action patterns.
- `Search.vue`: search and install UI, but backend search/install methods are not currently exposed.
- `Settings.vue`: manager status and capabilities.

The pages are currently optimistic about actions like search/install/update/uninstall. Until backend `App` methods exist for these operations, UI should either hide unsupported actions based on capabilities/backend exposure or show clear unavailable states.

### Components

`frontend/src/components/packages/PackagesDataTable.vue` and `packages-columns.ts` define the shared package table.

`VersionSelectButton.vue` assumes version lookup exists. It should eventually be shown only when the selected package's manager reports `listVersions` and the backend exposes version lookup.

Common UI components under `components/ui/` are local shadcn-vue style primitives.

### Events and Window Integration

`main.go` emits the Wails event `open_settings` from the macOS menu. `frontend/src/composables/useWailsEvents.ts` listens and routes to settings.

Window controls are isolated under `frontend/src/composables/useWindow.ts` and common chrome components.

## Data Flow

Startup:

1. Wails creates `App`.
2. `App.startup` initializes app root.
3. Registry constructs and preflights all adapters.
4. Config is loaded or created.
5. Logging is initialized.
6. Cache is initialized.
7. Cache is refreshed from registry-installed packages.

Installed packages UI:

1. Page calls `loadCachedPackages()` for fast display.
2. Page calls `reloadPackages()` to refresh backend cache.
3. Page calls `loadCachedPackages()` again.
4. Table filters and renders normalized package data.

Manager UI:

1. `ensureManagersLoaded()` calls `listManagers()`.
2. Backend returns adapter metadata from registry.
3. Frontend filters by `enabled` and `capabilities`.

## Design Rules Going Forward

1. `unipac-wails` is the maintained project. Do not modify the old Tauri project unless the user explicitly asks.
2. The frontend must not know the concrete package-manager set. No hardcoded manager lists, labels, icons, install commands, or special cases in frontend code.
3. The backend registry is the package-manager source of truth.
4. Capabilities should drive UI availability. If a manager cannot search, install, update, uninstall, or list versions, the UI should reflect that generically.
5. Pages and components should call `src/lib/api.ts`, not generated `wailsjs` bindings directly.
6. Generated Wails files under `frontend/wailsjs/` should not be edited manually.
7. Adapters should normalize package data into `manager.Package` before returning it.
8. Registry methods should validate manager existence, enabled state, and capabilities before calling adapter methods.
9. Cache should remain an implementation detail behind backend methods; frontend should not know the database schema.
10. Prefer small backend API methods that map to user workflows, not leaking adapter internals to the frontend.

## Suggested Near-Term Cleanup

- Remove frontend `managerLabelMap` and rely on backend `manager.Info.Name`.
- Replace direct `GetCachedPackages` import in `App.vue` with `loadCachedPackages()` or remove the startup console log.
- Add registry methods and `App` bindings for search/install/uninstall/update/version lookup before enabling those UI actions.
- Regenerate Wails bindings after adding exported `App` methods.
- Fix `manager.ErrorResult` to return `Success: false`.
- Fix registry loop-variable capture in `GetInstalledPackages()`.
- Guard `logging.Init` error handling when `LogFile` is nil.
- Decide whether an empty scan should clear the package cache or preserve the previous cache.
